## 3. 폴더 구조와 레이어 (기능 단위 구조)

```
src/
  components/
    layout/      Navbar, Footer, PageContainer
    ui/          GradeBadge, Chip, Segmented, PhotoThumb, MetricCard
  features/
    metric/      지표 키·라벨 사전, 프리셋 가중치, 점수→등급 계산(순수 함수)
    region/      시군구·읍면동 타입, API 함수, Query 훅
    tier/        티어리스트 응답 타입, API 함수, 훅
    …            페이지 스펙에서 추가 (review, compare, report, user 등)
  hooks/         useQueryState 등 범용 훅
  lib/           api<T>(), queryClient
  mocks/         mock 응답 데이터 (데이터 분석 결과로 생성)
  pages/         페이지 컴포넌트. features와 components를 조립만 한다
```

규칙:

- `pages/`는 다른 `pages/`를 import하지 않는다. 두 페이지가 같은 것을 쓰면 `features/`나 `components/`로 올린다.
- `features/A`가 `features/B`를 import하는 것은 허용하되, 순환은 금지한다. `metric`은 다른 feature를 import하지 않는다.
- `components/ui`는 도메인을 모른다. 예외는 `GradeBadge`(등급 타입)와 `MetricCard`(지표 키)로, `features/metric`의 타입만 import한다.
- 기존 개발 가이드 규칙(파일당 컴포넌트 1개 `export default function`, 토큰만 사용, 임의값 금지, 데이터 호출은 `api<T>()`)을 그대로 따른다.

### 데이터 흐름

```
page → features/*/use…Query()  (TanStack Query)
     → features/*/api.ts
         ├─ VITE_USE_MOCK=true  → mocks/ 의 데이터를 반환하는 함수 (지연 200ms 흉내)
         └─ 그 외               → api<T>('/…')
```

- 응답 타입은 `features/*/types.ts`에 둔다. 이 파일이 백엔드와의 **계약**이다. 각 페이지 스펙의 "API 계약" 절은 이 타입을 그대로 옮겨 적는다.
- 쿼리 키는 feature별 `queryKeys.ts`에 모은다. 예: `['tier', { month, scope }]`.
- `QueryClient` 기본값: `staleTime` 5분(월 단위 정적 데이터), `retry` 1, `refetchOnWindowFocus` false.
- 로딩·에러 표시: 페이지 단위 스켈레톤 + 에러 시 "다시 시도" 버튼. 공통 `QueryState` 래퍼 대신 각 페이지에서 `isPending`/`isError`를 직접 처리하고, 반복이 3곳 이상 생기면 그때 공통화한다.

## 5. 지표·점수 로직 (`features/metric/`)

### 지표 키와 라벨

| 키          | 화면 라벨   | 그룹      | 데이터 근거                                            |
| ----------- | ----------- | --------- | ------------------------------------------------------ |
| `quiet`     | 동네 조용함 | 동네 성격 | `day_inflow`(평일 낮 체류 ÷ 새벽 체류)가 낮을수록 높음 |
| `peer`      | 또래 밀도   | 동네 성격 | 또래 연령 비중                                         |
| `vibe`      | 저녁 활기   | 동네 성격 | `evening_vibe`(평일 저녁 유동 ÷ 평일 저녁 체류)        |
| `crowd`     | 시기 여유   | 시기·체류 | 해당 월 혼잡도가 낮을수록 높음                         |
| `overnight` | 숙박 성향   | 시기·체류 | 시군구 숙박 계수                                       |

- 화면 문자열은 반드시 `METRIC_LABEL[key]`에서 가져온다. 옛 라벨(비혼잡·한적함·야간 활동·장기체류 적합도)은 쓰지 않는다.
- `METRIC_KEYS`의 순서는 `['quiet', 'crowd', 'peer', 'overnight', 'vibe']`로 고정한다. 하위 등급 칩과 가중치 배열이 이 순서를 따른다.

### 타입

```ts
export const METRIC_KEYS = ['quiet', 'crowd', 'peer', 'overnight', 'vibe'] as const
export type MetricKey = (typeof METRIC_KEYS)[number]
export type Grade = 'S' | 'A' | 'B' | 'C'
export type PresetKey = 'quiet' | 'lively' | 'custom'
export type MetricScores = Record<MetricKey, number> // 0~100
export type Weights = Record<MetricKey, number>
```

(`erasableSyntaxOnly` 설정 때문에 enum 대신 `as const` 배열과 유니온 타입을 쓴다.)

### 프리셋

| 프리셋   | 라벨      | quiet                 | crowd | peer | overnight | vibe |
| -------- | --------- | --------------------- | ----- | ---- | --------- | ---- |
| `quiet`  | 조용한 곳 | 3                     | 3     | 1    | 1         | 0    |
| `lively` | 활기      | 0                     | 1     | 3    | 2         | 3    |
| `custom` | 직접 설정 | 고른 지표 1, 나머지 0 |       |      |           |      |

- 근거: 5개 지표는 A군(조용함·또래·활기)과 B군(시기 여유·숙박)이 서로 반대로 움직여서, 같은 가중치로 평균하면 B군이 묻힌다(종합 점수와의 상관 −0.06, −0.10). 그래서 "워케이션 밸류"는 선택한 프리셋의 종합 점수로 정의한다.
- 직접 설정의 입력 방식(토글 vs 가중치 슬라이더)은 W-02 스펙에서 결정한다. 이 문서의 함수는 두 방식 모두 `Weights`로 받는다.

### 계산 역할 분담

- **백엔드**: 지역마다 지표별 점수 `MetricScores`(0~100)를 준다. 점수는 해당 월·해당 범위(12개 시군구, 또는 비교 대상 읍면동 집합) 안에서의 백분위다.
- **프론트**: 종합 점수와 등급을 계산한다.
  - `composite(scores: MetricScores, weights: Weights): number`: 가중 평균. 가중치 합이 0이면 `NaN` 대신 0을 반환하고, 호출부는 "지표를 하나 이상 고르세요" 상태를 보여준다.
  - `toGrades(values: number[]): Grade[]`: 사분위 기준. 상위 25% S, 50% A, 75% B, 나머지 C. 동점은 같은 등급. 값이 4개 미만이면 순위 비율로 같은 규칙을 적용한다.
  - `metricGrade(score: number): Grade`: 하위 등급(개별 지표)은 이미 백분위이므로 고정 경계(≥75 S, ≥50 A, ≥25 B, 그 외 C)를 쓴다.
- 이 분담 덕분에 프리셋·직접 설정을 바꿀 때 API를 다시 호출하지 않고, W-01과 W-02가 같은 함수를 공유한다.

알려진 한계(페이지 스펙에서 화면 문구로 다룬다):

- 10월처럼 성수기에는 대부분 지역의 시기 여유가 C로 몰린다.
- 시군구 단위 동네 조용함은 주거형 도시에 유리하다.

## 6. URL 상태 규칙 (`hooks/useQueryState`)

```ts
function useQueryState<T>(
  key: string,
  parse: (raw: string | null) => T | null,
  defaultValue: T,
  serialize?: (v: T) => string,
): [T, (v: T) => void]
```

| 키        | 값                              | 기본값                        | 쓰는 곳                |
| --------- | ------------------------------- | ----------------------------- | ---------------------- |
| `month`   | `2025-01`~`2025-12`             | 데이터의 마지막 달(`2025-12`) | 전 페이지              |
| `preset`  | `quiet` \| `lively` \| `custom` | `quiet`                       | W-01, W-02             |
| `metrics` | 쉼표로 구분한 `MetricKey` 목록  | 프리셋 기준                   | `preset=custom`일 때만 |
| `tab`     | 페이지별                        | 페이지별                      | 각 페이지 스펙         |

- 파싱 실패(없는 달, 모르는 프리셋 등) 시 기본값으로 바꾸고 `replace`로 URL을 고친다(뒤로가기 기록이 쌓이지 않음).
- 값 변경은 `push`가 기본, 슬라이더처럼 연속으로 바뀌는 값은 `replace`.
- 페이지 이동 링크는 `month`, `preset`(그리고 `custom`이면 `metrics`)를 유지한다. 이를 위해 `useCarryLink(to)` 헬퍼로 경로에 공유 쿼리를 붙인다.
- 데이터 범위(2025-01~12)는 `features/metric/constants.ts`에 상수로 두고, 백엔드 연결 후 메타 API로 대체할 수 있게 한다.

## 8. 테스트와 CI

### Vitest

- 추가 패키지: `vitest`, `@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`, `jsdom`.
- 테스트 파일은 대상 옆에 `*.test.ts(x)`.
- 공통 기반에서 쓰는 테스트:
  - `composite`: 프리셋별 가중 평균, 가중치 합 0
  - `toGrades`: 사분위 경계, 동점, 4개 미만
  - `metricGrade`: 경계값 25/50/75
  - `useQueryState`: 잘못된 값 → 기본값 + replace
  - `Segmented`, `Chip`: 클릭 시 onChange, aria 속성

### Playwright

- Chromium만. `pnpm e2e`가 `VITE_USE_MOCK=true`로 개발 서버를 띄워 실행한다(`webServer` 설정).
- 공통 기반 E2E:
  1. 네비게이션으로 각 페이지에 들어가면 페이지 제목이 보인다.
  2. `?month=2025-10`으로 들어가 다른 페이지로 이동해도 `month=2025-10`이 유지된다.
  3. `?month=2099-01`로 들어가면 기본 달로 고쳐진다.
- 각 페이지 스펙은 "E2E 시나리오" 절에 1~3개 흐름을 적는다.

### CI

- 기존 `lint`, `format:check`, `build`에 `pnpm test`, `pnpm e2e`를 추가한다. Playwright 브라우저는 캐시한다.

### 문서 갱신

- `docs/개발-가이드.md`의 미정 항목을 갱신한다: TanStack Query 채택, 전역 상태 = URL 쿼리, 테스트 = Vitest + Playwright, 아이콘 = lucide-react, 폰트 변경.
